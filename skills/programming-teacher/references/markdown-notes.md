# Markdown 知识手册约定

## 何时读取

在新建、更新或整理本地 Markdown / Typora 学习笔记与知识手册前读取。教学大纲和练习簿的职责见 [curriculum-artifacts.md](curriculum-artifacts.md)。

## 先适配现有知识库

1. 确认知识库根目录，不自行假定用户路径。
2. 读取适用规则、README、模板、索引和同类笔记，优先沿用现有目录、命名、frontmatter、链接和排版。
3. Markdown 可能正在其它编辑器中修改；每次写入前重新读取目标文件最新内容。
4. 不覆盖无法合并的并发改动。发现结构或内容冲突时停止写入并说明位置。
5. 没有既有约定时才使用本文件默认结构，不为套模板创建空章节。

## 用户技术手册的职责

用户技术手册是交付给学习者的长期教材，不是 AI 老师的备课台账，也不是课堂聊天归档。即使暂时移开教学大纲和练习簿，学习者仍应能从目录进入某一章，理解先修关系，顺着正文、案例和验证步骤完成学习与复习。

技术手册保存脱离某次课堂仍然成立的内容：

- 解决什么问题
- 具体概念、语法、API、注解或操作
- 执行机制和时序
- 完整可对照案例
- 失败表现、易错点和排错方法
- 验证方式
- 资料来源、访问日期和适用版本

不写入：

- “本轮”“下一步”“今天先学”等课堂过程
- 阶段进度、掌握状态和复习日期；这些默认由教学大纲维护
- 面向 AI 老师的教学策略、掌握深度、状态证据和答案依赖审计表
- 成套练习题和答案；这些属于由练习文档与 `answers/` 实际文件组成的练习簿
- 未经实际发生而虚构的学习者心得或错误

概念说明使用通用表述，真实类名、路径和配置可以放进完整案例，便于回到工程对照。`K-*` / `T-*` / `E-*` 用于备课追踪，不作为手册目录骨架；确有检索价值时放在章末“进一步练习”或单独索引中，避免打断正文。

## 像课本一样组织

先设计全书目录，再写单个知识点。目录应体现学习者的认知路径，而不是文件被修改的时间顺序：

- 从基础概念到组合应用，再到边界、排错与工程实践
- 一章解决一个连贯主题，章与章之间有明确先修和过渡
- 同一机制的概念、API、时序、案例和易错点放在同一章附近
- 工具操作、错误速查、版本差异和术语表进入独立章节或附录，不穿插成正文杂项
- 新追问和新知识回填到最合适的既有章节；不能习惯性追加到文件末尾
- 正式练习留在练习簿；手册可以有少量“想一想”或小型观察任务，但不能复制成套题目、提示阶梯和答案

手册质量首先看阅读体验：目录是否清楚、概念是否逐步展开、术语是否一致、案例是否闭环、前后章节是否重复或断裂。不能仅凭覆盖了多少 `K-*`、包含多少代码块判断完成。

## 默认目录

没有现有约定时可按主题拆分：

```text
用户技术手册/
|-- README.md                 全书介绍、适用版本、阅读路线与目录
|-- 01-<基础主题>.md
|-- 02-<进阶主题>.md
|-- 03-<综合应用>.md
`-- appendices/
    |-- 工具操作.md
    |-- 错误排查.md
    `-- 术语与索引.md
```

单文件手册也必须具备等价的全书目录、章节顺序和附录边界。同一主题宜收拢，避免每次追问新建一个碎片文件或标题。工具安装、IDE 操作、快捷输入、构建和调试可集中到工具章节，但正文仍按实际任务可检索。

## 章节与小节结构

不要把每个 API 都写成互不相干的卡片。先确定这一章要帮助学习者形成什么整体能力，再按概念出现的自然顺序组织小节。可采用下面的章节骨架，但不要机械保留空标题：

```markdown
# <章节标题>

- 本章解决什么问题
- 先修知识
- 学完能够做什么
- 适用版本

## <第一个核心概念>

<从已有知识引入，解释用途、概念和必要术语>

## <机制或执行过程>

<谁在何时做什么，依赖什么，失败如何表现>

## <完整案例>

<从准备、实现到运行结果的完整可对照案例，并在代码后解释关键步骤>

## <边界、易错与排错>

- <真实、高价值且属于本章范围的易错点>

## <本章小结>

<串起概念关系，不重复整章正文>

## <进一步学习>

- 相关正式练习链接（可选，不粘贴题目与答案）
- 官方资料与适用版本
```

API 较多时应围绕一个完整任务串起来，在需要处解释各 API；不要连续堆方法表后让学习者自行猜测组合方式。章节内部可以用表格做对照和速查，但表格不能替代第一次学习所需的叙述、案例和运行结果。

代码块注明语言。实际输出与预期输出分开；未运行的内容明确标为“未在当前环境验证”。

## 案例组织

新手内容优先选择：

- 节前给完整案例，再按块解释；或
- 先讲用途、时序和要点，节末集中给完整案例。

不要在一节中穿插多段无法拼成终态的半截代码。课堂可以使用最小片段，知识手册应保留以后能够独立对照的完整实现。知识手册使用通用教学案例，练习专属的完整答案只放在练习簿体系；练习文档与 `answers/` 实际文件共同构成权威练习簿，编码答案源码以实际文件为准。二者代码完全相同时，手册使用精确链接，不把练习簿改成「见手册」或「见仓库」。

### API 案例的完整性

目标深度为 `会用`、`独立应用` 或 `排错与迁移` 时，只有 API 名称、方法签名、参数表或概念时序图不构成完整案例。学习者应能不打开练习答案，仅依靠本节完成一个同类最小调用。案例至少包含：

- 当前版本正确的依赖或 import；同一 API 在不同大版本包名变化时明确指出差异
- 对象从哪里来：构造、工厂方法、依赖注入或框架自动配置
- 可看懂的最小输入数据及必要模型；省略工程样板时明确指出沿用位置
- 完整调用语句，以及返回类型、实际输出或状态变化
- 必须捕获或理解的异常、失败输入和可观察表现
- 一种可执行的运行、测试、请求、日志、SQL 或调试观察方法

泛型、匿名类、Lambda、类型转换、注解属性等只要是完成调用不可缺少的语法，也必须在案例附近解释其局部作用。例如 API 需要 `TypeReference<List<Item>>` 时，不能只列出方法名：还要展示完整表达式、解释外层泛型、元素类型和匿名子类语法分别解决什么，并展示反序列化后的元素如何使用。

完整案例不得直接复制当前练习答案。应更换业务名和数据，保留相同知识结构，使它既能教学，又不替学习者完成题目。若找不到既完整又不泄题的案例，先调整教学或练习设计，不能退化成 API 清单。

## 工具与 IDE 操作

工具条目至少说明：

- 何时使用和解决什么问题
- 操作系统、工具与版本前提
- 完整命令或点击路径
- 完成标志
- 常见失败和排查方式
- 是否需要重启终端、IDE 或项目

快捷键和快速输入注明用途，不把记住按键写成掌握标准。界面路径可能随版本变化时，同时描述最终要观察的状态。

## 写入边界

- 在新阶段或新单元开课前，必须按已确定的大纲和答案反向知识审计完成对应手册章节，而不只是目录、标题或待补占位。它面向学习者，供课前预习、课堂对照和课后复习，但不能作为“已讲”证据。
- 实时教学开始时只核对教材是否就绪，不把核心手册写作留到教学之后。若发现缺失，先完成教材准备，再正式开课；完成手册后仍须在对话中完整授课，不能只给链接、摘要或维护汇报。
- 课堂结束后只根据学习者真实反馈做勘误、澄清、重排和高价值补充，不在课后第一次补齐本节核心内容。若本轮停在等待学习者回答，状态保持 `讲解中`，也不要把预测中的误区提前写成既成事实。
- 手册维护汇报保持简短，不能挤占或替代本轮教学正文。不能只给手册链接让学习者自行补上课堂中没有讲过的新知识。
- 新增内容前先确定它属于哪一章、与前后小节如何衔接；优先重写或扩充正确章节，不在文末建立“补充”“其它”“遇到的问题”式的长期垃圾桶。确需错误速查时放入排错附录，并链接回讲清原理的正文。
- 为每个需要查阅的概念、API、框架行为或工具操作保存具体文档入口、适用版本和检索关键词；优先官方中文，缺失或过时时指向官方原文。
- 不把练习的完整答案粘贴进知识手册；需要查看时链接到练习簿的准确练习编号、“完整答案”小节和对应答案文件。手册可以链练习簿，练习簿不能只链手册来代替答案文档与实际文件。手册可讲清职责与时序，不要因此把题目契约从练习簿删掉。
- 追问补进已有短段、表格或对应主题，避免保存成长问答聊天记录。
- 收拢重复论述时保留必要操作步骤、知识点和可对照案例。
- 删除、移动或批量重命名笔记前必须获得明确授权。
- 写入完成后立即按 [curriculum-artifacts.md](curriculum-artifacts.md#文档维护汇报) 的统一格式汇报维护位置。
